To establish mathematical and operational certainty that confirmation requests cannot be circumvented, reused, or hijacked, a dedicated security verification suite was implemented and executed: `tests/test_confirmation_security.py`.

### Security Properties Verified:

1. **Confirmation ID Binding**:  
   Every confirmation event generated by the Python runtime (`runtime_adapter._confirmation_prompt_fn`) instantiates a unique token formatted as `conf_<8 hex characters>` (e.g. `conf_1a903075`). The token is stored in the internal dictionary `_pending_confirmations` alongside a threading `Event` and bound directly to the blocking worker thread executing the tool.
2. **Single-Use Enforcement**:  
   When `chat.confirm` is dispatched, the handler acquires `_confirmations_lock`, resolves the event, and immediately calls `_pending_confirmations.pop(confirmation_id, None)`. The token is permanently destroyed.
3. **Duplicate Approval Prevention**:  
   Any subsequent attempt to submit an approval for the same `confirmation_id` immediately fails with `{"status": "not_found"}`. An action cannot be executed twice under any circumstances.
4. **Denial & Execution Halting**:  
   When the user clicks "Cancel / Deny" (`decision: "no"`), the event unblocks with decision `"no"`. The underlying tool dispatch aborts immediately, and the assistant generates the authoritative outcome: `"Action cancelled: user declined confirmation to execute '<tool>'."`
5. **Authoritative Runtime Timeout Enforcement**:  
   The confirmation timeout is governed exclusively by the Python runtime worker thread:
   ```python
   confirmed = evt.wait(timeout=120.0)
   with _confirmations_lock:
       entry = _pending_confirmations.pop(conf_id, None)
   ```
   If the user or React interface takes no action within 120 seconds, `evt.wait` returns `False`, the token is evicted under lock, and the decision defaults unconditionally to `"no"`.
6. **Bypass Immunity & Unconditional HIGH_RISK Blocking**:  
   Permission verification is executed by `tools.permissions.check_permission` and `execute_with_permission` directly within the Python process. React possesses no execution privileges. Even if a compromised client attempts to trigger a `HIGH_RISK` tool (or passes an admin flag), the Python security model returns `PermissionStatus.DENIED` and blocks execution unconditionally:
   > *"Action blocked: Tool '...' is classified as HIGH_RISK and cannot be executed automatically."*

- **Which module owns Job Storage?**  
  `brain.jobs.store.JobStore` and `brain.jobs.manager.JobManager`.
- **How is persistence actually implemented?**  
  In `brain/jobs/store.py`:

  `resolve_database_path(None)` resolves dynamically to `memory.db` (`DATABASE_FILENAME = "memory.db"`).
  Therefore, the `jobs` and `job_steps` tables are maintained **inside the authoritative `memory.db`**.
- **Was `jobs.db` created or modified by Phase 4?**
